# 原理与边界

这套方法能成立、以及它的边界在哪，都来自三个部件的真实机制。以下结论均经实测核对（包括 Ego 官方仓库 citrolabs/ego-lite 的 ego-browser 技能文档）。

## 三个部件

### 1. Muse from Meta 扩展

- Meta 官方发布的 Chrome 扩展，是 Muse 操作你本地浏览器的唯一入口。
- **档案（Profile）级安装**：装在哪个浏览器档案里，就在哪个档案里工作。
- **工作方式**：感知和操作页面走标签页 API + CDP。它**不看任务空间**——空间这个概念不在扩展的视野里，空间名对它不可见。
- 仅支持 PC 端 Chromium 系浏览器（Chrome、Ego 等）。

### 2. Ego 的任务空间（TaskSpace）

- 空间是**一个档案内的页面/工作区分组**：每个空间有自己的一组标签，仅此而已。
- **不隔离** Cookie、扩展、登录态、缓存——同一档案的所有空间共享这一切。
- 空间的生命周期是"用时生成"：官方入口是 `useOrCreateTaskSpace(name)` 一类"按名获取"语义——名字命中已有空间就复用，没有就当场创建。**空间不需要、也没有单独的预建/维护步骤**。
- 空间会随其标签全部关闭而消亡，也会在浏览器重启、升级后消失；恢复方式就是下次再按同名打开。

### 3. Muse 的设备浏览器通道

- Muse 在需要浏览器时可以选择"设备浏览器"（你这台电脑上装了扩展的浏览器），任务经扩展执行，页面状态回到 Muse。
- **实测行为（2026-11-13）**：一个任务在专属的任务窗口里执行——窗口里只有任务页面，后续操作锁定该窗口；用户在 Ego 里切换空间，任务不跟随、不受影响。也就是说任务与用户的页面天然分属不同窗口。
- 与之相对的是 Muse 自带的云浏览器：干净环境、无你的登录态。两者的分工是定版规则：**默认本地浏览器，云浏览器只用于用户明确指定采用它的任务**（含用户事先安排好、已在云浏览器上跑的定时任务）。无头浏览器/自建自动化通道不在本方案内。

## 由此得出的设计

既然扩展不认空间、空间又不做隔离，那么：

1. **窗口即边界（实测）。** 任务在自己的任务窗口里跑，里面只有任务页面；你的页面在你的窗口里。隔离是这个通道自带的，不需要任何一方做额外设置。
2. **空间是给人的秩序（可选）。** 把任务窗口归置进一个固定的 `Muse` 空间，好处只是你一眼能认出"这是 AI 的窗口"；它不提供隔离，也不是使用前提，不建空间照样成立。
3. **要硬隔离，用档案。** 第二个浏览器档案（Profile）有独立的 Cookie、扩展和登录态，扩展装在哪个档案就只能动哪个档案。代价：登录态两份维护。是否值得，取决于你的敏感程度。

## 代理（网络出口）

- Ego **不能按空间分配代理**：官方仓库里"给 Space 配 proxy"只是功能请求（issue #87），未实现。
- 代理的粒度只到**浏览器实例**：用独立的 `--user-data-dir` + `--proxy-server` 再启动一个实例，两个实例出口互不影响（macOS 上有实测无泄漏）；同一实例内的所有档案/空间共用同一出口。
- 结论：想让 Muse 的页面走不同出口，需要的是第二个实例，而不是第二个空间。

## 与「在 VPS 上养一个 Chrome」的区别

另一种常见做法目标相同——养一个登录态长期保存、AI 能直接操控的浏览器——但把浏览器搬到了服务器上：在 VPS 上安装 Chrome + Xvfb 虚拟显示，用 systemd 常驻（崩溃或手关都自动拉起），独立的用户数据目录存登录态，AI 走 CDP 调试端口操控，本人则经 VNC 远程桌面（两端口都只绑本机、靠 SSH 隧道进入）亲手完成第一次登录。区别在浏览器养在哪、信任模型完全相反：

| 维度 | 本方法（本地浏览器） | VPS 上养 Chrome |
|---|---|---|
| 运行位置 | 你自己的电脑、真实浏览器和真实显示 | 服务器，无真实显示，靠虚拟屏幕 |
| 可用性 | 电脑和浏览器开着才能用 | 24 小时常驻，你关机它也能跑 |
| 登录信任 | 你长期在用的设备和网络出口，站点通常直接认 | 机房 IP 的新设备登录，容易触发异地验证、手机验证和风控 |
| 隔离 | 靠任务窗口边界；同档案内登录态共享，要硬隔离得用独立档案 | 天然强隔离：独立机器、独立数据目录，不碰你日常浏览器 |
| 登录态存放 | 留在你自己的设备上 | 长期躺在服务器磁盘上，服务器被入侵或被快照就等于账号会话被端 |
| 接管方式 | 屏幕上实时可见，上手点一下就接管 | 先开 SSH 隧道再连 VNC，步骤多、画面有延迟 |
| 资源与维护 | 零额外成本，不用维护服务器 | Chrome + 虚拟显示 + 远程桌面很吃内存，小规格 VPS 跑不动，还要自己维护更新和安全 |

**怎么选**：主力账号、靠现成登录态做的日常领取和提交，优先本地这套——信任成本最低、接管最方便。确实需要电脑关机后也能跑、且能接受用一个专用小号（不要拿主力账号的长期会话去冒险）并自行承担服务器安全时，VPS 那套才有它的位置。两者可以并行，但不要默认互相替代。

若用 VPS 那套，三条底线不变：调试和 VNC 端口绝不对公网开放；SSH 私钥和账号密码不要贴进聊天，走安全的凭证保管；主力账号的登录态不要长期放在一台自己无法保证安全的服务器上。

## 能与不能

**能**：读页面与评论区、滚动加载、点击、填写表单、多步骤网页任务、用你的登录态访问站点。

**不能/不适合**：

- 扩展看不到"空间"，别指望靠空间实现权限隔离；任务也不会跟随用户切换空间，它锁定自己的任务窗口。
- 手机端无此通道（扩展仅 PC）。
- 遇强验证码/风控时应交还人工处理，不要反复硬闯。
